# Results

Raw measurements from live runs on Base Sepolia, Unichain Sepolia and Reactive Lasna. Every record carries the transaction hashes of each hop and explorer links, so each number can be checked on-chain.

| File | What it is |
|---|---|
| `SUMMARY.md`, `summary.json` | Aggregates (median, p95, max, success rate, race capture) from every file below, generated by `npm run summary` in `harness/` |
| `flowB-*.json` | Flow B loops: Morpho repayment → Lasna react → queue paid. A 3-loop smoke test and a 30-loop run |
| `flowC-*.json` | Flow C loops: shortfall → reserve fronts → relayer reimbursed on Unichain. A 30-loop run (29 ok, 1 failed) and a 2-loop rerun |
| `race-*.json`, `race-run.log` | The latency race: 60 rounds, 6 per cell, 5 competitor delays × 2 speeds |
| `flowC-run.log` | Console log of the 30-loop flow C run |
| `batch-*.json`, `batch-run.log` | Batch continuation (flow D): 40 withdrawals from 40 wallets paid by ONE repayment across 2 callbacks, with FIFO order, gas and every transaction. Produced by `npm run batch` |
| `replay-race.json`, `replay-run.log` | The 60 race rounds plus the Lasna transactions that reacted to each repayment, for the dashboard's replay. Produced by `npm run replay` from the recorded race file; nothing is re-measured |
| `case-study-flowC.json`, `case-study-run.log` | The cross-chain loop that is not in the 31/32, reconstructed step by step from chain data. Produced by `npm run casestudy`; see [`docs/CASE_STUDY_FLOW_C.md`](../docs/CASE_STUDY_FLOW_C.md) |
| `aborted/` | **Runs that were discarded, kept for transparency.** See below |

## Notes on the data

- **One flow C loop is not in the 31/32, and it did not fail in the flow.** Loop 0 of the 30-loop run was recorded as failed because the harness's *cleanup* step (`commitCredit()` on the sibling vault) ran out of gas: it was sent with a gas limit of 34,915 and used all of it. The loop's payout and reimbursement had already happened, which is checked from the chain events in [`case-study-flowC.json`](case-study-flowC.json). The harness now adds a 30% gas buffer to every transaction, and a 2-loop rerun with the fix succeeded. The failed record stays in the data as an attempt.
- **`aborted/` also holds the logs of two interrupted batch runs.** In the first, the 40-withdrawal settlement succeeded on-chain (queue empty 2,491 ms after the repayment) and the script then crashed while reading evidence: 40 parallel `balanceOf` calls hit a dropped connection on the public RPC. In the second, a public-RPC timeout hit a `requestWithdraw` that had in fact been mined, so the script saw an error for a step that had succeeded. Both led to fixes in `batch.ts` (retries, evidence reads a few at a time, and staging that checks on-chain state before and after every step so it can resume); the complete record in `batch-*.json` is from a run that resumed the second one's partly staged queue and finished it.
- **`aborted/` holds two discarded race attempts.** In the first, the competitor bot was slow (it read the market and estimated gas before sending), which let the queue "win" against an instant competitor, so the result flattered Sluice. It was replaced by a bot that fires immediately with a fixed gas limit and no pre-read. The second `aborted/` race file is the partial run of that slow bot, and `diagnostic-c0.json` is the 4-round check that exposed the problem and validated the fix.
- **Wall-clock times** are measured by polling every ~150 ms, so each includes up to one poll interval of observation delay. **Block timestamps** resolve to 1 second, and chains' clocks differ slightly, so wall-clock is the more precise measure.
- **"+6 Lasna blocks (~legacy)"** adds delay on Omni via `delayBlocks`. It approximates legacy speed; it is not a run on the legacy network.
- **The competitor bot** runs on one machine through a public RPC, so its own transaction takes about 1.2 to 1.4 s to land. An in-region bot would be faster, so the "0 s" row is not a speed limit.
